## Context and evidence

Proposed after the xj-2jb spike; maintainer acceptance is pending. No production change is proposed for immediate merge.
MEASURED by an embedder at pin 4995c39: 1,226,271 translator map entries, 4,573,138 resident 4 KiB pages (17.45 GiB), within 17.8 GiB process RSS. Map entries are not a reliable unit count.
MEASURED here: main 54fad17, macOS arm64, Rust 1.95, Cranelift 0.115.1, 16 KiB host pages; repeated `Backend::materialize` of lifted `mov eax,7; hlt`, explicit Speed, distinct guest entries. These are synthetic small blocks, not the embedder workload or its configured tiers.

READ: `cranelift-jit-0.115.1/src/memory.rs`: `allocate` page-rounds a new allocation; `set_readable_and_executable` calls `finish_current`, flushes caches, protects RX, and loses unused tail capacity. `Drop` intentionally leaks; `JITModule::free_memory(self)` releases the whole module, and x86jit never calls it. macOS coalesces adjacent entries: a second 1,000-unit None run had 13 entries, while a 10,000-unit None run had 1,024. Every measured baseline unit still consumed one resident 16 KiB page.
READ: `lib.rs:2664` has two lazy modules for default/nondefault MXCSR specializations, not one module per unit; construction is at 3077, per-unit finalization at 3732. `libcalls.rs` supplies a closed symbol resolver. Cache upgrade/invalidation drops raw pointers and clears link slots; its epoch gates publication/predictors, not execution reclamation.
READ: `codemap.rs:1` retains immutable AVL insertion paths, source locations, trap tables and frame recipes indefinitely, including after backend drop; it has no unregister, and rejects overlapping host ranges. Storage is O(n log n). The large process RSS beyond packed code in the prototype includes these metadata, compiler/module tables and allocator retention; it is not attributable solely to code pages.
MEASURED: instrumentation observed zero external relocations in 1,184 native backend buffers and 1,592 cross-ISA fault fixtures; 30 explicit libcall witnesses emitted `Abs8` relocations on both encoders. This covers tested shapes, not every possible lowered unit.
READ: helpers, counters, link slots, guest-base specialization and other runtime pointers are baked constants; chains use indirect slot loads. Constant pools are inside the compiled buffer; no module data objects are declared. Cranelift can introduce libcalls, so “all code is relocation-free” is not a valid invariant without checking.
READ: decision-13 uses a static landing stub plus per-unit offset-based trap/source tables and unwind recipes, registered at the final executable PC range. Moving an unchanged buffer requires rebasing its registered range, not regenerating its frame recipe; reused addresses require safe metadata replacement.

## Decision

The maintainer chose **option A** on 2026-11-10: upgrade Cranelift and plug in an x86jit-owned `JITMemoryProvider`. The Context and evidence above is the unchanged spike record; its pending-acceptance statement describes the proposal at measurement time.

Target **Cranelift 0.135.8 / Wasmtime v48.0.8**, the newest released Cranelift compatible with the Rust 1.95 gate as checked on 2026-11-10. The [v48.0.8 JIT manifest](https://github.com/bytecodealliance/wasmtime/blob/v48.0.8/cranelift/jit/Cargo.toml) declares 0.135.8 and inherits [Rust 1.95.0 from the workspace](https://github.com/bytecodealliance/wasmtime/blob/v48.0.8/Cargo.toml#L220-L227); the [upstream releases](https://github.com/bytecodealliance/wasmtime/releases) identify v48.0.8 as the latest v48 patch. Newer release lines require [Rust 1.96.0 for v49 / Cranelift 0.136](https://github.com/bytecodealliance/wasmtime/blob/v49.0.0/Cargo.toml#L221-L228) and [Rust 1.97.0 for v50 / Cranelift 0.137](https://github.com/bytecodealliance/wasmtime/blob/v50.0.1/Cargo.toml#L222-L229). The controlling check is `cargo +1.95 clippy`; the dev shell's rustc 1.96.1 does not authorize a higher MSRV. Raise the workspace `rust-version` from 1.88 to **1.95** with the upgrade and keep the Cranelift crates on the same release. This is an implementation requirement; this docs-only acceptance does not change the manifests.

The provider was [introduced by #10512](https://github.com/bytecodealliance/wasmtime/commit/56148ad9a82f708e42a47003cbee0df5ca2aa365), first in 0.120.0 / v33. Its argument enum `JITMemoryKind` became publicly exported in **0.134.0 / v47**, through [#13632](https://github.com/bytecodealliance/wasmtime/commit/61ba992de8ded7e281771b1e079167c11f387ed3): compare the [v46 exports](https://github.com/bytecodealliance/wasmtime/blob/v46.0.0/cranelift/jit/src/lib.rs) with the [v47 exports](https://github.com/bytecodealliance/wasmtime/blob/v47.0.0/cranelift/jit/src/lib.rs). The chosen version has both the provider and the public types needed to implement it outside Cranelift. The upgrade includes the MemFlagsData/interned flags, declare_var API and ExtFuncData.patchable migrations identified by the spike.

x86jit implements `JITMemoryProvider` and owns allocation, publication and lifetime. Reserve large regions: **128 MiB on Linux/FreeBSD**; on macOS, logical regions within **one process-wide MAP_JIT reservation shared across backends**. Use dense bump allocation with the required code/buffer alignment, constant pools and veneer space, without per-unit page rounding or discarding the unused tail on every finalization. After reclamation, allocate from coalescing free lists as well as unused tails. The built-in Arena provider's page-rounded sealing is insufficient.

W^X follows the OS: Linux uses shared `memfd` RW/RX alias views; FreeBSD uses shared `shm_open(SHM_ANON)` RW/RX views; macOS uses MAP_JIT and per-thread write protection (`pthread_jit_write_protect_np`) around all compiler and relocation writes, respecting the embedder's hardened-runtime entitlement/callback policy. Each alias view obeys W^X, although its backing remains writable through the RW alias; policies requiring stronger writer restrictions need writer gating. Never remove execute permission from pages another vCPU may execute. Complete copying and relocation, maintain caches for the writable and executable views as required, and establish instruction-pipeline synchronization for executing threads **before publication**. A local arm64 ISB in the prototype is not a multithread publication guarantee.

The single-pointer API requires explicit integration. The spike found, and [v48.0.8's provider trait](https://github.com/bytecodealliance/wasmtime/blob/v48.0.8/cranelift/jit/src/memory/mod.rs#L19-L38) confirms, that `allocate(size, align, kind)` returns one pointer; `finalize` and whole-provider `free_memory` supply neither a second address nor per-unit release. [CompiledBlob](https://github.com/bytecodealliance/wasmtime/blob/v48.0.8/cranelift/jit/src/compiled_blob.rs) uses that pointer for copying, relocation writes and relocation-site arithmetic; [JITModule](https://github.com/bytecodealliance/wasmtime/blob/v48.0.8/cranelift/jit/src/backend.rs) also uses it for symbol addresses, code ranges and `get_finalized_function`. Simply returning an RW pointer and translating only the entry point is insufficient: PC-relative relocations and references to other allocations would still use the wrong address.

Choose a **narrow integration patch to the pinned cranelift-jit**, proposed upstream, that keeps distinct writable and executable addresses for each blob while retaining `JITMemoryProvider` for allocation/finalization. The provider returns the RW allocation and records its RX translation in shared allocation state; the integration obtains both addresses from that state. Copy and patch through RW; compute relocation sites/targets and veneers using final RX addresses; expose RX addresses for symbols, code ranges, finalized entries and metadata. On macOS both addresses are the same MAP_JIT address. This patch is part of option A's implementation scope, not an existing upstream capability or a switch to option B's standalone compile-buffer/relocation path. Keep Cranelift's module relocation machinery and x86jit's closed libcall resolver; audit the upgraded relocation output and reject unsupported kinds before publication. Preserve compiler context metadata before clearing it. Witness both absolute and PC-relative relocations, including cross-unit targets and veneers, under nonzero RW/RX offsets.

Expose to embedders `code_bytes_live`, `code_bytes_retired`, cumulative emitted bytes; live/retired unit counts; logical region counts and mapping-view counts; reserved/committed bytes; reusable free bytes, unused tails and largest free extent; metadata bytes and allocation failures. Observer consumers need publish/retire/release events and allocation generation ids. Distinguish allocator commitment from physical-resident measurements and avoid counting the two alias views as two physical allocations.

Reclamation is **per unit**, using allocation handles/generations and retirement notifications for invalidation, tier replacement, rejected completions and backend teardown. Unlink retired entries and flush predictors, prevent fresh execution from entering them, then wait for both an **execution grace period and a signal-reader grace period**. Existing invalidation epochs alone do not establish that grace period. Remove the old executable codemap ranges and safely replace metadata before an address is reused; reclaim obsolete immutable codemap roots, trap/source tables and unwind recipes under the same reader protocol. Retire module-side records and stale relocation/symbol references as well, so Cranelift's tables cannot retain callable references to reused storage or grow indefinitely with retired units.

After grace and range removal, return extents to free lists with coalescing, decommit wholly free pages (including the shared backing behind both aliases), and release empty Linux/FreeBSD regions. Retain the single macOS reservation while decommitting its free pages. Preserve live entry addresses; do not compact live code. The provider's whole-module `free_memory` is **not** the retirement/reclamation mechanism; any final teardown using it must independently meet the same no-execution/no-reader lifetime obligations.

Preserve **decision-13 landing pads and fault metadata**, registering trap/source offsets and unwind recipes at the **final executable range**. Reused ranges require safe metadata replacement. Preserve the **VFloatMov workaround**: it addresses an LLVM defect (doc-27) and is unaffected by upgrading Cranelift. Re-validate every witness suite after the upgrade: **trap sites, unwind/prologues, libcalls, fences/memory ordering and the native oracle**. Review codegen differences in hot benches and run the real-program ladder; compiler-version changes are not assumed behaviorally or performance neutral.

## Alternatives, cost and consequences

ASSUMED estimates are focused engineer-days for one engineer with access to all three OSes; they include allocator, retirement and regression work, not just initial code placement. They remain spike estimates, not implementation commitments; option A must also cover the explicit dual-address integration and its witnesses.

| Option | Effort / risk | Expected code entries and resident backing for the reported workload | Reclamation / AOT | Outcome and reason |
|---|---|---|---|---|
| A: upgrade + custom provider | 18–30 days; compiler/API and allocator risk | With a custom dense provider: about `2*ceil(S/128 MiB)` alias mappings, macOS one reservation; backing near S. Built-in Arena still seals page-rounded segments per finalize, so does not cure padding. | Provider has only whole-module free; add our own retirement. AOT address-table prerequisite remains. | **Accepted:** own memory through the provider while retaining Cranelift's JITModule and relocation machinery; explicitly fund the compiler migration and dual-address integration. |
| B: 0.115 buffers + owned arena | 15–24 days; lifetime/OS risk, stable codegen | Same dense bound; at S=17.45 GiB, about 280 alias mappings or one macOS mapping. Actual S/live fraction is unknown. | Free lists after a new grace protocol; direct basis for AOT buffer storage. | **Rejected:** retaining old codegen avoids the migration but makes x86jit own a separate compile-buffer placement and residual-relocation path. The maintainer chose the newer compiler and provider integration. |
| C: batch JITModule finalization | 2–4 days; publication latency/queue changes | Tiny blocks may share pages; multi-page units still get separate allocations. Neither N/batch mappings nor a few hundred entries is guaranteed; expect much of the 17.45 GiB to remain. | No per-unit reclamation; eventual memory growth remains. AOT extraction still outstanding. | **Rejected:** batching cannot guarantee dense storage or bounded mappings and does not solve per-unit reclamation. |

S means emitted live code plus alignment/veneer space, not total RSS. Dual aliases share physical backing, but RSS accounting can count both views (up to roughly 2S); use PSS/unique resident backing separately. Module/codemap/heap overhead prevents predicting an exact new process RSS from the embedder's mapping histogram.
All options leave the AOT B1 prerequisite: replace baked process addresses with runtime tables and persist ISA/version-keyed code plus fault metadata. Relocation-free machine code alone does not make current buffers reusable across processes. The old AOT plan's whole-chunk RW/RX toggling needs the concurrency correction above.

## Implementation phases (bead briefs)

These are ordered implementation bead briefs, not a second task board; no beads are created by this docs-only decision update.

1. **Cranelift upgrade alone.** Move all Cranelift crates to 0.135.8 and raise workspace `rust-version` to 1.95, completing the API migrations with the existing storage path. Require equal behavior and performance: all preserved witness suites, native-oracle CI, JIT benchmarks against `bench/baseline.json` on the same machine/configuration, codegen-difference review of hot benches, and the ladder. Explain and resolve regressions before introducing the provider so allocator changes do not obscure compiler changes.
2. **Memory provider, counters and bound test.** Implement dense OS regions, the explicit RW/RX JIT integration, publication/cache/pipeline protocol and embedder counters. Add a **100,000-unit bound test** checking map entries and RSS on **arm64 and x86-64**, with emitted/alignment/veneer bytes and metadata accounted separately. For a fresh packed run, use the measured prototype bounds as the macOS starting point: at most four code entries, resident code at most emitted bytes + 16 bytes/unit + one host page, and total RSS at most 64 MiB + 4096 bytes/unit. Establish explicit Linux/FreeBSD bounds for two alias views per 128 MiB region and report PSS/unique backing as well as RSS; do not equate dual-view RSS with physical code consumption. The test must fail against the page-per-unit baseline and show bounded mapping growth with dense bytes, not unit count.
3. **Retirement and reclamation.** Add unit handles/generations, execution and signal-reader grace periods, codemap range removal/replacement and metadata/module-table retirement, coalescing free lists, reuse and page decommit. Witness invalidation, tier replacement, rejected completions and backend teardown; demonstrate that repeated retire/recompile cycles bound code storage and metadata and that stale readers/entries cannot observe a reused generation.
4. **Stress and platform tests.** Exercise Linux, **FreeBSD where available**, and macOS, with native arm64/x86-64 coverage. Stress concurrent compilation/publication/execution, signals and fault recovery, unwind, SMC, tiering, address reuse, decommit, allocation failures, alias relocations and cross-thread instruction visibility. Re-run the preserved witness suites, performance/codegen review and ladder with the complete lifetime path. Record unavailable platform coverage explicitly rather than treating the single-thread macOS spike as a substitute.

## Spike validation and retained artifacts

MEASURED validation: release backend library tests 109 passed, 4 ignored (serial relocation audit); arena execution example agreed with interpreter; seven unwind tests passed with arena placement. An initial parallel audit run failed because diagnostic stderr printing was inherited across a fork; the serial audit passed. No native x86-64, Linux or FreeBSD run was available.
MEASURED bounded 100,000-unit arena rerun passed: <=4 code entries, resident code <= emitted bytes + 16 bytes/unit + one host page, total RSS <=64 MiB + 4096 bytes/unit (270 leaf entries, one code entry, 319,045,632 RSS bytes). Baseline failed the same bounds at 1,000 units. Reclamation/alias/platform tests remain follow-up work.
The throwaway `code_memory_spike.rs` and `code_memory_spike.patch` are retained outside the repository tree in the investigator's scratch directory. They are historical measurement tools, not the accepted provider implementation.
